# Aqara 0.3.0 — Agent and Cloud modes

One `aq` workflow now supports both the default Agent connection and Cloud
control through the Aqara Home app's API, including supported lock commands.

## What changed

- `aq mode` shows both modes and marks the current one. Use `aq mode cloud`
  or `aq mode agent` to switch; the choice persists across Alfred sessions.
- Cloud mode discovers capabilities from current Aqara endpoint definitions
  and device metadata. Native controls include advertised lock/unlock, power,
  brightness, and color temperature, with Agent fallback preserving the other
  device controls and existing scenes.
- U100 through its M3 and U300 accepted cloud Unlock followed by Lock, with
  fresh reads reporting the requested states. The tested U100 route required
  no phone-held pairing key or LAN connection.
- Multiple accounts, regions, and homes remain supported. Cloud home links
  associate differing API IDs explicitly; device names never route a command.
- Agent and Cloud retain separate connections, home selections, catalogs,
  and status preferences. A reset affects only the selected mode. Switching
  modes invalidates old command selections, including a switch during a
  lock-password dialog.
- Both modes use one bundle, package, and stable update channel. User guides,
  Alfred's embedded help, and API research notes describe the unified setup.

## Install or upgrade

Download [Aqara-0.3.0.alfredworkflow](https://github.com/schwark/alfred-aqara/releases/download/v0.3.0/Aqara-0.3.0.alfredworkflow)
and open it in Alfred. From v0.2.7, `aq workflow:update` also starts the upgrade;
confirm it in Alfred's import dialog. Existing Agent connections are preserved,
and Agent remains the default for installations without a saved mode choice.

For Cloud, run `aq mode cloud` and follow
[README-cloud.md](https://github.com/schwark/alfred-aqara/blob/v0.3.0/README-cloud.md).
On the first switch, a configured earlier parallel installation is copied into
Cloud mode, including sessions, signing identity, and home links. Existing
Cloud data is never overwritten. After verifying the new setup, disable or
remove the earlier parallel workflow in Alfred. Otherwise, `aq import` can
seed an unconfigured Cloud mode with the Agent profiles and fallback keys.

## Current limits

Cloud uses undocumented app APIs and remains experimental. Full command
coverage requires Agent fallback; additional native Cloud scene execution
has not been live-tested. Cloud sessions do not refresh automatically; use
`aq login` if a session expires. Lock tests establish accepted requests and
reported-state changes, without independent observation of mechanical movement
or validation of every device/firmware combination. Failed writes are not retried.

## Validation and package contents

All 157 tests pass on Python 3.9 and 3.14. Installed-workflow checks cover the
mode picker, migrated sessions, lock command choices, and returning to Agent
without sending device commands. Release checks verify bundle/version identity,
the explicit package allowlist, documentation links, and private-data scans.

The workflow contains no saved accounts, home/device records, credentials,
signing constants, captures, APKs, or research tools. Downloads are checked
against GitHub's SHA-256 digest and the expected bundle/version before import.
macOS with Alfred 5 Powerpack and Python 3.9 or newer is required; the workflow
needs no additional Python packages.
